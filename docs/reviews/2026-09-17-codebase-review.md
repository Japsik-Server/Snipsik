## 3. 확인된 문제

### R01. URL 헬스체크의 요청 대상 제한 부재

- **위치:** `src/services/sinkClient.ts:823–835`, `src/commands/link.ts:809–815`
- **문제:** 일반 사용자가 `/link check`에 전달한 URL을 봇 서버가 그대로 GET 요청합니다. 애플리케이션에 명시적인 프로토콜·내부 네트워크·리다이렉트 목적지 검증이 없습니다.
- **영향:** 서버 측 요청 위조(SSRF) 위험이 있습니다. 실제 접근 가능 범위는 VM 네트워크와 외부 통신 정책에 따라 달라지며, 이번 리뷰에서는 확인하지 않았습니다.
- **권장 수정:** HTTP(S) 허용 목록, 실제 연결 대상 및 리다이렉트별 목적지 검증, 네트워크 계층의 내부 서비스 접근 제한을 함께 적용합니다.
- **완료 기준:** 금지 목적지는 연결 전에 거부하고, 리다이렉트에도 동일 정책이 적용되는 격리된 테스트를 추가합니다. 운영 내부 주소로 재현 요청을 보내지 않습니다.

### R02. CRC32를 소유권 식별자로 사용

- **위치:** `src/services/slugManager.ts:57–59`, `:96–102`
- **문제:** 사용자 ID를 CRC32로 줄인 뒤 슬러그 접미사와 비교해 소유권을 판정합니다. 32비트 값의 Base36 표현은 일대일이지만, Discord 사용자 ID에서 CRC32로의 변환은 일대일이 아닙니다.
- **영향:** 서로 다른 사용자의 해시가 같으면 수정·삭제·통계 권한 검사에서 구분할 수 없습니다. 실제 서비스 사용자 간 충돌은 확인하지 않았습니다.
- **권장 수정:** 링크와 원본 Discord 사용자 ID의 명시적 소유권 매핑을 저장하고 검사합니다. 기존 링크의 소유권 이전 정책도 설계해야 하며, 충돌 가능한 해시만으로 소유자를 확정하면 안 됩니다.
- **완료 기준:** 서로 다른 소유자가 동일한 표시용 해시를 가지더라도 권한 판정은 원본 사용자 ID로 분리되는 테스트를 추가합니다.

현재의 [상세 사양서](../SPECIFICATION.md)는 DB 역할을 설정·Watch 저장으로 제한하므로, 명시적 소유권 매핑 도입은 해당 제약을 바꾸는 설계 결정이 필요합니다. 이 리뷰 문서 자체로 사양을 변경하지는 않습니다.

### R03. 버튼 인터랙션 ACK 지연

- **위치:** `src/events/interactionCreate.ts:152–167`, `:173–194`; 페이지 이동·선택 등에도 유사 패턴 존재
- **문제:** 삭제 확정 시 삭제 API와 대시보드 조회를 마친 뒤에야 `interaction.update()`를 호출합니다.
- **실패 조건:** 외부 API 응답이 느려 3초를 넘으면 실제 삭제는 완료됐지만 Discord에는 인터랙션 실패가 표시되고 기존 확인 화면이 남을 수 있습니다.
- **권장 수정:** API/DB 작업 전에 `deferUpdate()`, 완료 후 `editReply()`를 사용합니다. 수정 모달의 `getLink()` → `showModal()` 흐름은 defer 후 모달을 열 수 없으므로 별도 설계가 필요합니다.
- **완료 기준:** 느린 API mock에서도 ACK가 외부 작업보다 먼저 발생하고, 작업 실패 후 사용자에게 결과를 표시하는 테스트를 추가합니다.

### R04. Watch 초기 캐시 로드 실패 후 복구 부재

- **위치:** `src/events/ready.ts:31–49`, `src/services/watchService.ts:25–37`
- **문제:** 시작 시 DB 연결 실패로 Watch 로드를 건너뛰거나 로드 오류를 로그만 남기고 종료합니다. Watch에는 초기화 상태와 자동 재시도가 없습니다.
- **실패 조건:** DB가 복구돼도 캐시는 비어 있어 기본 `inherit` 사용자의 기존 감시 채널이 자동 복구되지 않습니다. DB 기반 목록과 캐시 기반 처리·제거 판단도 불일치할 수 있습니다.
- **권장 수정:** 초기화 완료 상태, 백오프 재시도, 재로딩과 변경 작업 사이의 경합 보호를 추가합니다.
- **완료 기준:** 최초 DB 실패 후 복구 시 기존 Watch 설정이 자동 적용되고, 로딩 도중 등록·삭제한 설정도 보존되는 테스트를 추가합니다.

### R05. 배포 준비 완료 판정 불충분

- **위치:** `scripts/deploy.sh:145–164`, `src/events/ready.ts:17–49`
- **문제:** `Logged in as` 로그는 DB·설정 캐시 초기화 전에 출력됩니다. 그 로그가 없더라도 약 20초간 컨테이너가 실행 중이면 성공으로 처리합니다.
- **영향:** 필수 기능이 준비되지 않았는데 배포 성공으로 판정하고 이전 컨테이너를 제거할 수 있습니다.
- **권장 수정:** Discord 연결과 필수 캐시 초기화를 함께 확인하는 readiness 상태를 정의하고, 기한 내 준비되지 않으면 롤백합니다. 단순히 HEALTHCHECK를 추가하는 것보다 그 검사가 무엇을 보장하는지가 중요합니다.
- **완료 기준:** 프로세스는 실행 중이지만 필수 초기화가 실패한 경우 배포가 성공하지 않는 테스트를 추가합니다.

### R06. 잘못된 만료 입력을 무기한 링크로 처리

- **위치:** `src/utils/time.ts:4–23`, `:51–52`, `src/commands/link.ts:563–568`, `src/events/interactionCreate.ts:488–493`
- **문제:** 미입력과 잘못된 입력이 모두 `undefined`로 반환됩니다. 호출자는 두 경우를 구분하지 않고 생성합니다. 큰 상대 기간은 유효하지 않은 Date를 만들고 `toISOString()`에서 예외가 발생합니다.
- **실패 조건:** `1hour`처럼 지원하지 않는 값을 입력해도 만료 제한 없는 링크가 생성될 수 있습니다.
- **권장 수정:** 미입력·성공·실패를 구분하는 반환 타입, 날짜 범위 및 미래 날짜 정책, 사용자 오류 안내를 추가합니다.
- **완료 기준:** 오타·범위 초과·과거 날짜·빈 입력·정상 기간을 각각 테스트하고, 오류 입력에서는 생성 API가 호출되지 않도록 합니다.

### R07. 마크다운 조합에서 URL 오추출

- **위치:** `src/events/messageCreate.ts:14`, `:32–50`, `:229–235`
- **문제:** URL 바로 앞 두 문자로만 스포일러를 판단하고, 괄호보다 스포일러를 먼저 제거합니다. 다른 마크다운 포맷과 인접 링크는 충분히 분리하지 못합니다.
- **로컬 확인 사례:**
  - `||see https://example.com/path||`의 닫는 `||`가 URL에 남습니다.
  - `||https://example.com/path||)`는 괄호 제거 후에도 `||`가 남습니다.
  - `**https://example.com/path**`의 닫는 `**`가 URL에 포함됩니다.
  - `[a](https://example.com/a)[b](https://example.com/b)`가 하나의 후보로 합쳐집니다.
- **영향:** 최소 URL 길이 조건을 통과하면 잘못된 목적지가 저장되고, 본문 치환 시 포맷도 손상될 수 있습니다.
- **권장 수정 및 완료 기준:** 포맷 문맥과 URL 범위를 보존하는 추출 방식으로 바꾸고 위 조합을 회귀 테스트에 추가합니다. 합법적인 URL 쿼리의 `|`를 보존하는 기존 테스트도 유지합니다.

### R08. 긴 설정값이 설정 패널 렌더링을 막음

- **위치:** `src/utils/ui.ts:690–698`
- **문제:** 입력 검증을 통과한 제외 도메인 전체를 하나의 텍스트 컴포넌트에 넣습니다. 헤더·마크다운을 더한 출력 길이는 입력 길이보다 큽니다.
- **로컬 확인:** 도메인 50개, 쉼표 포함 3,989자 입력은 정규화를 통과하지만 출력 시 빌더의 4,000자 제한으로 `ExpectedConstraintError`가 발생했습니다.
- **영향:** 설정은 저장됐지만 응답이 실패하고, 이후 설정 패널 조회도 같은 데이터 때문에 실패합니다.
- **권장 수정 및 완료 기준:** 메시지 전체 텍스트 예산에 맞춰 일부 표시·페이지 처리를 적용합니다. 입력 상한 근처의 설정을 저장한 뒤 다시 조회해도 렌더링되는 테스트를 추가합니다.

### R09. 수정 모달에서 빈 필드 삭제 의도 유실

- **위치:** `src/events/interactionCreate.ts:567–573`
- **문제:** 제목·태그·설명을 지우면 `빈 문자열 || undefined`가 되어 요청 JSON에서 필드가 빠집니다.
- **영향:** API에 삭제 의도가 전달되지 않아 기존 값이 유지됩니다.
- **권장 수정 및 완료 기준:** API 계약에 맞는 명시적 빈 값을 전달합니다. 비밀번호의 ‘비우면 유지’ 규칙과 구분하고, 기존 필드를 비웠을 때 실제 요청에 제거 값이 포함되는 테스트를 추가합니다.

### R10. 대시보드 조회 상한과 전체 통계 표시 불일치

- **위치:** `src/commands/link.ts:48–51`, `:81–83`, `src/utils/ui.ts:65–82`
- **문제:** 전체 개수는 count API에서 가져오지만, 클릭 합계와 선택 메뉴 페이지는 최대 100개 검색 결과를 기반으로 합니다.
- **영향:** 101개 이상인 사용자는 나머지 링크를 대시보드에서 선택할 수 없고 누적 클릭은 과소 표시됩니다. `/link list`, `/link admin user`도 최대 1,000개 조회 범위를 전체처럼 취급합니다.
- **권장 수정 및 완료 기준:** 서버 측 페이지네이션과 집계를 연결하거나 조회 범위를 명시합니다. 조회 상한을 넘는 데이터에서 전체 개수·합계·선택 가능 범위가 일치하는지 테스트합니다.

### R11. 조회 상한 때문에 기존 링크 재사용 누락

- **위치:** `src/events/messageCreate.ts:128–139`
- **문제:** 전체 사용자 대상 URL 검색에 `limit: 20`을 적용한 후 소유자를 필터링합니다.
- **실패 조건:** 반환된 20개가 다른 사용자의 링크이고 본인 링크는 그 뒤에 있으면 기존 활성 링크를 놓치고 새로 생성합니다. 실제 빈도는 Sink 결과 순서와 데이터 분포에 따라 달라집니다.
- **권장 수정 및 완료 기준:** 가능한 경우 검색 단계에 소유자 조건을 적용하거나 추가 페이지를 조회합니다. 본인 링크가 첫 페이지 밖에 있는 경우도 재사용하는 테스트를 추가합니다.

### R12. Watch 동시 등록 시 중복 행 생성

- **위치:** `src/services/watchService.ts:123–141`, `src/db/schema.ts:12–20`
- **문제:** 캐시 확인과 INSERT가 원자적이지 않고 `(guild_id, channel_id)` 유니크 제약도 없습니다.
- **로컬 확인:** 같은 채널에 대한 동시 등록 mock에서 INSERT 두 번, 성공 두 번이 발생했습니다. 메모리 Set은 한 건처럼 보이지만 DB에는 중복이 남습니다.
- **권장 수정 및 완료 기준:** 기존 중복 정리 후 복합 UNIQUE와 conflict 처리를 적용합니다. 실제 제약이 있는 테스트 DB에서도 동시 등록 결과가 한 행인지 검증합니다.

### R13. Sink 공통 요청의 명시적 타임아웃 부재

- **위치:** `src/services/sinkClient.ts:284–303`
- **문제:** 헬스체크와 달리 링크 API 공통 요청에는 애플리케이션이 정한 AbortSignal 기반 시간 제한이 없습니다.
- **영향:** 응답 또는 본문 수신이 오래 걸리면 인터랙션과 동일 URL의 in-flight 작업이 지연됩니다.
- **권장 수정:** 본문 수신까지 포함한 총 시간 제한을 적용합니다. 조회 재시도와 생성·수정의 ‘서버 반영 여부 불명’ 처리를 분리하고 변경 요청을 무조건 재시도하지 않습니다.
- **완료 기준:** 응답 헤더 지연·본문 지연 시 기한 내 종료되고, in-flight 상태가 정리돼 후속 요청이 가능한 테스트를 추가합니다.

### R14. 길드 설정 로드 실패 시 제외 도메인 무시

- **위치:** `src/services/guildConfigService.ts:487–494`, `:531–541`, `src/events/messageCreate.ts:210–251`
- **문제:** 사용자 설정은 미로드 시 자동 처리를 보류하지만, 길드 설정은 기본값을 반환하면서 재시도합니다.
- **실패 조건:** user/watch 캐시는 준비됐지만 guild 캐시만 실패하면 서버 제외 도메인과 서버별 길이 제한을 무시할 수 있습니다.
- **권장 수정 및 완료 기준:** 필수 길드 설정이 준비되기 전에는 자동 처리를 보류하거나 유효한 이전 스냅샷을 사용합니다. 일부 캐시만 실패해도 제외 도메인의 URL이 Sink로 전송되지 않는 테스트를 추가합니다.

### R15. 시크릿을 받는 서드파티 액션이 가변 참조 사용

- **위치:** `.github/workflows/pr-agent.yml:62–65`
- **문제:** `the-pr-agent/pr-agent@main`에 API 키와 쓰기 권한이 있는 GitHub 토큰을 전달합니다. 실행 코드가 저장소 변경 없이 바뀔 수 있습니다.
- **권장 수정 및 완료 기준:** 검증한 커밋 SHA로 고정하고 정기 갱신 절차를 마련합니다. 다른 액션도 같은 정책으로 점검합니다. 실제 공급망 침해가 발견됐다는 의미는 아닙니다.

### R16. 자동 배포와 수동 마이그레이션의 순서 미보장

- **위치:** `.github/workflows/deploy.yml`, `scripts/deploy.sh`; 수동 절차는 `README.md:46–48`
- **문제:** 새 코드는 자동 배포되지만 스키마 적용은 별도 수동 작업입니다. 배포 경로에 적용 상태 검사가 없습니다.
- **실패 조건:** 새 컬럼을 사용하는 코드가 DB보다 먼저 배포되면 설정 조회가 SQL 오류로 실패할 수 있습니다.
- **권장 수정:** 배포 전 적용 상태 검사 또는 별도 마이그레이션 단계를 마련합니다. additive 변경과 롤백 호환성을 우선하며, 무조건적인 `db:push` 자동화로 해결하지 않습니다.
- **완료 기준:** 필요한 마이그레이션이 미적용된 상태에서는 새 코드 배포를 차단하거나, 검증된 순서로 적용 후 배포합니다.

### R17. 컨테이너 교체 중 스크립트 중단 시 복구 공백

- **위치:** `scripts/deploy.sh:89–124`
- **문제:** 기존 컨테이너를 이름 변경·정지한 뒤 새 컨테이너를 시작합니다. 시작 실패 분기에는 롤백이 있지만, 교체 중 스크립트 자체가 중단되면 그 분기에 도달하지 못할 수 있습니다.
- **영향:** 실행 중인 봇 없이 정지된 백업만 남을 수 있습니다.
- **권장 수정:** 처리 가능한 종료 신호·오류에는 trap 기반 복구를 적용하고, 강제 종료처럼 trap으로 복구할 수 없는 경우에도 재실행 시 상태를 복원하도록 설계합니다. 두 봇을 동시에 실행하는 방식은 중복 메시지 처리 위험부터 검토해야 합니다.
- **완료 기준:** 교체 단계별 중단 후 재실행 시 정상 컨테이너가 복구되는 로컬 배포 테스트를 추가합니다.

## 4. 외부 계약·운영 환경 확인이 필요한 항목

### C01. 응답 unwrap 과정에서 페이지 메타데이터 유실

- **위치:** `src/services/sinkClient.ts:348–352`, `:752–765`
- `{ data: [...], total, cursor }` 형식이면 공통 요청이 배열만 반환하면서 바깥 `total`과 `cursor`를 버릴 수 있습니다. mock에서는 `total: 100`이 목록 길이인 `1`로, cursor가 `null`로 바뀌었습니다.
- **추가 확인:** 현재 Sink 인스턴스의 실제 목록 응답 계약을 확인합니다. 이 형식을 사용한다면 목록 API는 원본 envelope 또는 메타데이터를 함께 유지해야 합니다.

### C02. 잘못된 2xx 응답을 정상 링크로 정규화

- **위치:** `src/services/sinkClient.ts:303–309`, `:372–377`, `:405–424`
- 응답 정규화에서 요청 slug/URL을 보충합니다. `200 {}` mock에서 조회는 URL 없는 링크로, 생성은 요청값을 복사한 링크로 성공 처리됐습니다.
- **추가 확인:** 실제 API의 성공 acknowledgment와 링크 객체 응답을 구분하고 필수 필드 계약을 확인합니다. 엔드포인트별 스키마 검증으로 잘못된 응답을 성공으로 숨기지 않아야 합니다.

### Supabase RLS 운영 전제

[아키텍처 문서](../ARCHITECTURE.md)의 보안 모델은 PostgREST Data API 비활성화를 전제로 RLS를 비활성화합니다. 이번 리뷰는 그 전제를 근거로 RLS 비활성화 자체를 확정 취약점으로 분류하지 않았습니다.

운영 Data API 설정이나 실제 DB 역할은 확인하지 않았습니다. 웹 연동·Data API 활성화 전에는 테이블 권한과 RLS 정책을 다시 설계하고 검증해야 합니다.
